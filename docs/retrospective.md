11月22日から2日間で、「共通の場から魔素の束を摘み、別の世界の住人を招いて3×3の庭で育てる」ボードゲームを作り、1人（CPU と）と通信対戦（ブラウザどうし）で遊べる形で公開した（工程0〜9、版 0.14.2）。企画はその前に別のチャットで、11/16 から固めた（ボードゲーム 構想メモ → 企画まとめ）。Auto Battler・Arc-en-ciel Creator・Celestial Alchemy・Aether Atelier のふり返り（各リポジトリの `docs/retrospective.md`）の続きとして読む。

## 結論（先に3つ）

- **ルールの心臓部を「状態＋操作 → 新しい状態」の純粋な関数にし、種つきの乱数・CPU・自動対戦を最初に作ったのが、最後まで効いた。** 通信（ホストが本物の状態を持ち、人ごとに見え方を分ける）、記録の再現、600ゲームの調整、エフェクト（描き直しの前後の盤面をくらべる）が、全部同じ部品の上に乗った。

## うまくいったこと

- **純粋な関数と種つきの乱数。** 「記録をコピー」を `tools/replay.mjs` で同じゲームに戻せ、通信では `viewFor` で山や乱数、手入れ中のほかの人の動きを隠せた。エフェクトは、効果の動いた順を盤面に残すだけで「開花を左上から順に光らせる」ができた。
- **判定の表（Docs、OK／直す／保留）で毎回まとめて決めた。** フェーズ1の D1〜D18、工程9の6回とも、番号とコメントで返ってきた。直す所はコメントに直し方まで書いてあった（D5「2文字くらいの略、記号が違えば分かる、全文は説明で」など）。
- **調整の前提（Q1〜Q7）を先に決めてから、まとめて合わせた（前作の教訓）。** 人の考え方「拡張を混ぜたときに強くなるのは OK。複数の拡張を混ぜたときだけ異常に強くても直さない」が先に分かったので、直す範囲が基本セットに絞れた。決めた範囲は `test/balance.test.js` で守っている。
- **拡張を PR で足す手順を、最初の拡張で実際に試した。** ブランチ・PR・CI（書き方の確かめとテスト）を通して取り込めたので、ほかの人が札を足す道ができた。
- **game-ui（画面の採点）で問題を数字にし、本物の画面に案を当てて人が選んだ。** カードから説明まで 1132px → 310px、育てるボタンまで 563px → 63px、摘むボタンのずれ 51px → 0。

## うまくいかなかったこと

| 起きたこと | 原因 | 次はこうする |
|---|---|---|
| 別の回線（スマホの 5G）とつながらなかった。工程8の調整を止めて直した | Trystero が appId から自動で選ぶ合図の中継5か所のうち、通るのは2か所だけだった。TURN もなかった。通しの試しが同じ Wi-Fi とブラウザ2タブだけだった | 通信のフェーズの終わりに、別の回線どうし（片方はスマホの携帯回線）で最後まで通す。合図の中継と TURN は最初に決め、確かめるページを先に作る |
| 夜空の絵を入れたら、カードの一覧と通信の確かめが白い背景になった | 絵を CSS の変数で入れ、変数を入れるのはゲームの画面だけだった。変数のないページで背景の指定ごと無効になった。見た目を変えたあとに全ページを開かなかった（Aether の手順20と同じ） | 見た目の共通部品は、どのページでも読む作りにする（なければ代わりの値）。見た目を変えたら、コミットの前に全ページを開く |
| 遊び方の文が古いまま（導きの「足す」など）、ゲームの流れの図がなく、対戦中にルールを開けなかった | 言葉を変えた（工程7・9）とき、遊び方を直す決まりがなかった。遊び方ははじめの画面にしかなかった | 言葉を変えたら、遊び方とことばの一覧も同じコミットで直す。遊び方は1つの部品にして、どの画面からも開けるようにする |
| 最初の先番がいつも席0で、人は毎回最後に始まりのカードを招いていた | フェーズ1のルールの決めごと（D1）に「最初の先番」を書かず、テストも席0 を前提にしていた | ルールの決めごとに「席の順・最初の先番・同点」を入れる。1人と通信の両方で、席の偏りがないかを見る |
| 草原の模様が黄色くうるさかった | 絵の乱数の関数が負の値を返していた。見本の絵（崖・門など）もその誤りのまま OK をもらっていたので、新しい絵だけ直した | 絵の部品の乱数にも「0〜1に入る」テストを付ける |
| CPU の強さを選ぶ所がないのに「かしこい」の話が出て、人が戸惑った | 「かしこい」は調整で測るために作った道具で、ゲームに出すかを決めず、報告でも言わなかった | 作った物がゲームに出るのか、道具だけなのかを報告で言う |
| 先番をランダムにしたら、調整の守りのテスト（180ゲーム）が揺れで落ちた（600×3ゲームでは問題なし） | 守りの線が、測りの揺れ（1枚 ±0.15）に対して余裕が小さかった | 守りのテストは、先番や席を順に回して揺れを抑えてから線を決める |
| ほかの作業のファイル（`docs/ui.md`、`.claude/launch.json`）をコミットしかけた | `git add -A` を使った | 自分のファイルだけを名前で足す（記憶に入れた） |

## 人と AI の役割

- **人が強かったところ：** 遊んで分かる不健全さ（後出し）と不満（白い背景・閉じられない一覧・先番の固定）、ボードゲームの作法（対面の配置・手元の早見表）、世界観の絵の案（夜空の島・門・房）、通信の試し（回線を変える・アカウントを作る）、調整の考え方。
- **AI が強かったところ：** ルールの心臓部とテスト、600ゲームの自動対戦と測り、通信の切り分け（確かめページ・中継の選び直し）、画面の採点と案の比べ、ドット絵、エフェクト、判定の表と計画のメモの書き足し。
- **AI が弱かったところ：** 変えたあとに全ページを見直すこと（前作と同じ）、別の回線での通信を先に疑うこと、ルールの細部で「書かれていない当たり前」（最初の先番）を拾うこと。

## 次のゲームで使う手順

前作の20の手順に、今回の教訓を足した（21〜24）。

1. 好きなゲームの面白さを抜き出し、別のチャットで企画を固める。企画まとめ（Docs）を「正」にして、作るチャットにはリンクを渡す。
2. 企画に「変えないこと」と「ジャンルのお約束」を書く。
3. 中身の全体の形を表で決める。
4. 名前と見た目の方向を早めに決める。
5. フェーズは「中身を足す」「見た目」「最終の調整」を分ける。1フェーズは1〜2日で終わる大きさに。
6. フェーズごとに遊んで、番号と理由で答える。決まったことは計画のメモと企画まとめの両方に。
7. 「忘れないようにメモ」は Issue にし、マイルストーンを付ける。AI はフェーズを閉じる前に残りの Issue を並べる。
8. 大量に作るものは、人が見て直せる表やアーティファクトにする。試し描き・試作を数個見せてから量産する。
9. 調整の前提を決めてから、最後にまとめて合わせ、固定する。固定した数字はテストで守る。
10. 調整のあとに足すものは、「難易度を変えるか」を先に決める。
11. 操作の不満は小さくても、すぐ言う。
12. 長い計算は、締め切りと「寝る前にどこまで」を書く。
13. （パズル）素材や部品ごとに「いちばん素直な部品では、なぜだめか」を企画で1行書き、早めに確かめる。
14. （パズル）ソルバーの限界を最初に測り、大きさの上限をそこから決める。
15. （生成）量産の前に、計算の目安と人の順位が合うかを数問で確かめる。
16. （生成）「同梱するだけ」か「その場で作る」かを先に決める。
17. （工場・配置）新しい仕組みは、本編の前に試作の区画で1つずつ遊ぶ。中身の表の段階で、新しい仕組みの区画にお手本を1つ置いて広さを決める。
18. （調整）依頼や目標の量は、工夫する人の配置で決める。配置を文字列で渡せる仕組みを早めに入れ、人の配置をもらって量を測り、テストに入れる。
19. （調整）お手本の前提（最初の形か、改善した形か）を書き、報告で言う。人の計算とずれたら、まず前提を比べる。
20. （画面）中身を足すフェーズの終わりに、全ページ（タブ・図鑑・説明・地図）を見る。新しい道具や素材は、図鑑とマウスの説明を同じコミットで足す。分け方（タブ）は、最後の中身の数で決め直す。
21. **（通信）通信のフェーズの終わりに、別の回線どうし（片方はスマホの携帯回線）で最後まで通す。** 合図の中継と TURN は最初に決め、つながらないときの確かめページを先に作る。
22. **（画面）見た目の共通部品（背景・色・絵）は、どのページでも読む作りにする。見た目や言葉を変えたら、コミットの前に全ページを開く。** 遊び方とことばの一覧も同じコミットで直す。
23. **（ルール）「席の順・最初の先番・同点」を、ルールの決めごとに入れる。** 1人と通信の両方で、席の偏りがないかを見る。守りのテストは席を回して揺れを抑える。
24. **（画面）遊び方はゲームの流れの図つきで1つの部品にし、対戦中も開けるようにする。** 画面の直しは、採点（数字）→ 本物の画面に案を当てる → 人が選ぶ、の順で。

### 頼むときのひな形（今回の分を足した）

```

■正の文書：企画まとめのリンク（決まったことはここに書き足す）
■変えないこと：遊びの柱、ジャンルのお約束、固定した数字 など
■前提：試すときの条件、遊び方（ふつうの人／工夫する人）、お手本は最初の形か改善した形か
■目標：数字と、その測り方（何を相手に、何回測るか）
■素材・部品の役目：それぞれ「いちばん素直な部品ではできないこと」
■大きさの上限：ソルバーやヒントが間に合う範囲、区画の広さはお手本で確かめる
■人の配置：送った図面はテストに入れ、量の目安にする
■ルールの当たり前：席の順・最初の先番・同点の扱い
■通信：試す回線（同じ Wi-Fi／別の回線・スマホの携帯回線）
■画面：全ページの一覧（見た目や言葉を変えたら全部開く）、画面のまとめ（ID）の場所
■任せてよいこと：数値の当てはめ、生成、テスト、絵
■必ず確認してほしいこと：遊びの柱にかかわる変更、全体に効く値の変更、2通りに読める指示
■人が遊ぶ回数：試作は○回まで、1回○問
■残っているメモ：Issue 番号（フェーズの終わりに読み上げる）
■報告に入れてほしいこと：足した機能の場所、お手本の前提、全ページの確認結果、ゲームに出る物か道具だけか、作れなかったもの
■締め切り：日本時間 ○月○日 ○時
■説明：やさしい日本語で、結論から
```

## 残っていること

- 別の回線どうしで、最後まで通した対戦はまだ（5G でつながることは確かめた）。通信の部屋での投了も、テストだけで2台ではまだ試していない
- TURN は Metered の無料枠（月 500MB、1ゲーム4人で約3MB）。足りなくなったら考える
- 拡張だけで遊ぶと、色の偏りが大きい（白2%・赤9%）。直さないと決めた（工程8 X1）
- CPU はゲームでは「ふつう」だけ（「かしこい」は調整の道具。人の判断で今のまま）
- 遊んだ人からのフィードバック
